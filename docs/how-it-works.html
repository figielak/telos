Telos 0.2 · pre-alpha

Jak działa Telos

Telos to pamięć projektu dla agentów kodujących. Kilka małych plików markdown w .telos/ i proste narzędzie telos, które o nie dba.

Jaki problem rozwiązuje

Każda nowa sesja agenta zaczyna od zera. Agent nie wie, do czego służy projekt, gdzie co leży, co jest następne ani dlaczego coś zostało zrobione tak, a nie inaczej. Musi to za każdym razem odtwarzać z kodu albo pytać ciebie.

Telos zapisuje te odpowiedzi w repozytorium i podaje agentowi krótki status na początku każdej sesji. Planowanie, pisanie kodu i testy pozostają zwykłą pracą agenta. Telos tylko zapisuje stan, nie narzuca procesu.

Z czego się składa

Pliki pamięci
Zwykły markdown w .telos/, commitowany razem z kodem. Każdy plik ma limit rozmiaru, więc pamięć nie puchnie.
CLI telos
Czyta i aktualizuje pliki. Nie wywołuje żadnego modelu, więc działa przewidywalnie. Nigdy nie zapisuje nic do gita.
Wtyczka Claude Code
Pięć poleceń /telos:… i trzy hooki: status na starcie sesji, strażnik gita i ostrzeżenie przed odtwarzaniem usuniętych rzeczy.

Cykl pracy

Dwa pierwsze kroki robisz raz. Potem powtarzasz plan, pracę i zamknięcie dla każdej fazy.

  1. RAZ

    telos init

    Wykrywa stack i polecenia sprawdzające (testy, lint, build), tworzy .telos/ i dopisuje krótki blok zasad do AGENTS.md. Można uruchomić ponownie: istniejące pliki zostają.

  2. RAZ, W ISTNIEJĄCYM KODZIE

    /telos:map

    Tworzy mapę: krótki indeks MAP.md i po jednej notatce na obszar kodu w .telos/areas/ (punkty wejścia, niezmienniki, decyzje). Proponuje też treść PROJECT.md do twojego potwierdzenia.

  3. NA POCZĄTKU FAZY

    /telos:plan dodaj logowanie linkiem z maila

    Dodaje fazę do ROADMAP.md i zapisuje jeden plik planu: cel, kryterium ukończenia i listę zadań z polami do odhaczenia. Zadaje najwyżej jedną rundę pytań.

  4. W TRAKCIE

    Zwykła praca

    Pracujesz z agentem jak zawsze. Gdy zadanie jest gotowe, agent odhacza je w pliku fazy. Przed edycją kodu czyta tylko notatkę obszaru, którego dotyka, a nie całe repozytorium.

  5. NA KOŃCU FAZY

    /telos:close

    Nieodhaczone zadania blokują zamknięcie. Agent uruchamia sprawdzenia, aktualizuje notatki obszarów, które się zmieniły, zapisuje wpis w HISTORY.md i ustawia status na następną fazę. Gdy sprawdzenie nie przejdzie, faza zostaje otwarta.

  6. NASTĘPNA SESJA

    Status na starcie

    Nowa sesja dostaje automatycznie krótki status (do 1200 znaków) i od razu wie, na czym stanęło. To samo pokazuje /telos:status.

Pracowałeś bez Telosa? Uruchom /telos:catchup. Porówna gita z notatkami i zaktualizuje obszary, których dotyczyły zmiany. Status i listę zadań fazy poprawiasz wtedy sam.

Prawdziwy status z repozytorium Telosa. Tyle wystarcza, żeby wiedzieć, co robić dalej i gdzie szukać reszty.

Pliki pamięci

PlikOdpowiada na pytanie
PROJECT.mdPo co jest projekt i jakie ma twarde zasady, konwencje oraz rzeczy poza zakresem.
MAP.mdGdzie co leży. Krótki indeks: struktura, lista obszarów, podpowiedzi „gdzie szukać”.
areas/<nazwa>.mdJak działa jeden obszar kodu: punkty wejścia, niezmienniki, decyzje, odrzucone podejścia, pułapki. Czytany tylko wtedy, gdy praca go dotyczy.
ROADMAP.mdJakie są fazy. Jedna linia na fazę ze statusem i kryterium ukończenia.
phases/NN-nazwa.mdCo dokładnie robimy w tej fazie: cel, kryterium, lista zadań.
STATUS.mdCo teraz i co dalej: faza, zadanie, następny krok, blokery.
HISTORY.mdDlaczego. Datowany dziennik decyzji i Delete-zone, czyli lista usuniętych ścieżek i podejść, których nie wolno odtwarzać.
config.jsonUstawienia: stack, polecenia sprawdzające, limity, opcje gita.

STATUS, ROADMAP i HISTORY zmienia tylko CLI (telos status set, telos roadmap set, telos history add). Dzięki temu format plików się nie rozjeżdża.

Skąd wiadomo, że notatki są aktualne

Każda notatka obszaru zapisuje w nagłówku commit, względem którego była ostatnio sprawdzona (kotwicę), oraz ścieżki, które opisuje. telos stale porównuje kotwicę z gitem i bez udziału modelu wypisuje:

  • obszary, których pliki zmieniły się od kotwicy,
  • odwołania w notatkach do plików, które już nie istnieją,
  • zmienione pliki, które nie należą do żadnego obszaru.

Liczba nieaktualnych obszarów pojawia się też w statusie na starcie sesji. /telos:close i /telos:catchup aktualizują notatki i przesuwają kotwice.

Bezpieczniki w Claude Code

HookCo robi
Start sesjiWstrzykuje status. Działa też po wznowieniu, /clear i kompaktowaniu kontekstu.
Strażnik gitaBlokuje git push, --no-verify, git add -A i git add ., git reset --hard oraz --amend wypchniętego commita.
Delete-zoneOstrzega, gdy agent edytuje ścieżkę wpisaną jako usunięta, i podaje powód usunięcia. Nie blokuje.

Instalacja

Wymagane: Git i Node.js w wersji 20.10 lub nowszej. Telos nie ma żadnych zależności.

Claude Code

/plugin marketplace add figielak/telos
/plugin install telos@telos

Codex i inne agenty

git clone https://github.com/figielak/telos
npm install -g ./telos

Potem w swoim repozytorium: telos init.

W agentach innych niż Claude Code nie ma poleceń /telos:… ani hooków. Zamiast tego prosisz agenta: „uruchom telos ctx plan i wykonaj to, co wypisze”. Zasady gita są wtedy tylko opisane w AGENTS.md, nic ich nie wymusza.

Kiedy warto, a kiedy nie

Warto

  • Projekt trwa tygodnie i wraca się do niego po przerwach.
  • Decyzje i ich powody nie wynikają z samego kodu.
  • Pracuje nad nim kilka sesji lub kilku agentów.

Nie warto

  • Małe, jednorazowe zadania. Zwykły Claude Code albo krótki CLAUDE.md wyjdzie taniej.
  • Repozytorium, w którym ta sama wiedza jest już spisana w dokumentacji.

Pamięć kosztuje tokeny. W benchmarku wersji 0.1 Telos był droższy w każdym mierzonym zadaniu przy podobnej skuteczności, dlatego wersja 0.2 zostawiła samą pamięć. Wersja 0.2 nie była jeszcze mierzona w ten sposób. Czy pamięć pomaga w twoim projekcie, sprawdzisz poleceniem telos resume-test: zadaje ono twoje pytania świeżym sesjom z pamięcią i bez niej i porównuje wyniki oraz koszt. Uwaga: to płatne sesje, po dwie na każde pytanie.
